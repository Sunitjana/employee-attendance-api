This review compares the supplied starter `app/main.py` with the assignment contract. Function names are used instead of line numbers because line numbers change as the implementation evolves.

| # | Where | What was wrong | How to notice it | How it was fixed |
|---:|---|---|---|---|
| 1 | `compute_late_minutes` | The starter rebuilt the shift start using the punch-in datetime's date and did not correctly account for IST calendar dates, overnight shifts, or the strict 10-minute grace boundary. | For a 09:30 shift, 09:40:00 must be 0 late minutes, while 09:40:01 must be 10. An overnight punch-in after midnight belongs to the previous shift date when it is earlier than `shift_end`. | Normalize the instant, derive the attendance date in IST, build the shift-start instant in IST, and only mark late when the difference is strictly greater than 600 seconds. Then floor the full minutes since shift start. |
| 2 | `compute_work_hours` | Python's built-in `round()` can use ties-to-even rounding, which does not guarantee the assignment's half-up rule. | Test a duration whose hours fall exactly on a half-cent boundary and compare it with half-up rounding. | Calculate elapsed whole seconds and use `Decimal` with `ROUND_HALF_UP` to two decimal places. |
| 3 | `compute_overtime` | The starter calculated overtime against the same calendar date and counted positive minutes without enforcing the 30-minute qualification threshold. Overnight shifts were therefore handled incorrectly. | Test a punch-out 29 minutes after shift end, one exactly 30 minutes after shift end, and a shift ending after midnight. | Calculate the actual shift-end instant, moving it to the following day for an overnight shift, floor whole elapsed minutes, and report overtime only when elapsed seconds are at least 30 minutes. |
| 4 | `health` | The starter returned `{"status": "ok"}` without checking MongoDB connectivity. | Stop MongoDB and call `GET /health`; a healthy response would be misleading. | Ping MongoDB and return HTTP 503 when the database cannot be reached. |
| 5 | `create_employee` and index setup | Checking for an existing employee before inserting is not race-safe. Two concurrent requests can both pass the check. | Send simultaneous requests with the same `emp_code`. | Create a unique index on `employees.emp_code` and translate `DuplicateKeyError` to HTTP 409. The database constraint, not the pre-check, is the concurrency guarantee. |
| 6 | Employee and punch-in request models | The starter models did not validate the required formats and business constraints for employee codes, email addresses, calendar dates, shift times, status values, or timestamps. | Send malformed dates, invalid statuses, a float timestamp, explicit `null`, or equal shift start/end times. | Add Pydantic constraints and validators, including strict integer timestamps and validation of actual calendar dates. Invalid requests return HTTP 422. |
| 7 | Employee creation and timestamp helpers | The starter used naive local datetimes and returned timestamps in formats that did not follow the API's epoch-millisecond contract. | Change the host timezone or inspect `created_at`, `punch_in`, and `punch_out` response types. | Use UTC-aware instants internally, truncate instants to whole seconds, and convert timestamps at API boundaries between epoch milliseconds and BSON datetimes. |
| 8 | `list_employees` pagination | The starter used `skip = page * page_size`, which skips the first page when `page` starts at 1; it also lacked bounds for pagination inputs. | With `page=1&page_size=10`, the first ten matching employees should be returned. Try `page=0` or a page size above 100. | Use `(page - 1) * page_size`, require page >= 1, and restrict page size to 1–100. |
| 9 | `list_employees` total | The starter counted all employees instead of counting documents matching the optional department filter. | Filter by a department and compare `total` with the number of employees in that department. | Call `count_documents()` using the same filter used to retrieve the page. |
| 10 | `list_employees` ordering | The starter did not define a stable sort order, so page boundaries could be inconsistent. | Request consecutive pages repeatedly and check for missing or repeated employee codes. | Sort by `emp_code` before applying skip and limit. |
| 11 | `punch_in` employee lookup | The starter did not handle an unknown employee before accessing the employee's shift fields, which could produce an HTTP 500. | Punch in using an `emp_code` that does not exist. | Require the employee first and return HTTP 404 for an unknown employee. |
| 12 | `punch_in` timestamp and attendance date | The starter used the host's local timezone and treated a falsey timestamp as if it had not been supplied. It did not implement the contract's UTC truncation and IST/overnight attendance-date rules. | Supply an explicit epoch-millisecond timestamp near UTC midnight, or an invalid zero/negative/seconds timestamp, and test an overnight shift. | Validate supplied timestamps explicitly, convert epoch milliseconds to UTC, truncate to whole seconds, and calculate the attendance date from IST shift rules. |
| 13 | `punch_in` write path | The starter's check-then-insert sequence did not protect against simultaneous punch-in requests and exposed a MongoDB ID as an API `id` field. | Send simultaneous punch-ins for the same employee/date and inspect the response body. | Enforce a unique compound index on `(emp_code, date)`, handle duplicate-key conflicts as HTTP 409, and serialize only the fields specified by the API contract. |
| 14 | `list_attendance` query and pagination | The starter loaded all matching attendance documents into Python, sorted and paginated in memory. This is inefficient at the specified scale and does not use database-side pagination. | Test against a large collection and inspect memory/time usage or the explain plan. | Build one MongoDB filter, count matching documents, sort in MongoDB, and apply skip/limit in the database. Indexes support the common filters and sort. |
| 15 | `list_attendance` validation, ordering, and serialization | The starter accepted unvalidated date/status/page inputs, had no deterministic secondary sort, and exposed `id` while returning timestamps in a representation other than epoch milliseconds. | Try malformed dates, an unsupported status, invalid pagination, equal-date records, and inspect response field types. | Use typed date/status/query parameters with bounds, sort by date descending and employee code ascending, and serialize records with epoch-millisecond timestamps and no public MongoDB ID. |

## Reviewed and retained

- Loading `.env` with `load_dotenv()` is appropriate because its default behavior does not override real environment variables that are already set by the process.
- The default shift times are consistent with the supplied starter's intended defaults; the implementation validates them and rejects equal start and end times.
- The API's derived attendance fields are computed by the application and stored for analytics, rather than being accepted from a client request.
- The remaining endpoints marked as TODO in the starter were implemented as Part B of the assignment: punch-out, regularization, employee monthly analytics, department summary, late leaderboard, department trend, and the explain endpoint.
